# Database

PostgreSQL via Supabase. Migrations are plain SQL in `supabase/migrations/`,
applied in filename order by `npm run db:migrate` and recorded in
`schema_migrations`, so re-running is safe.

| File | Contents |
| --- | --- |
| `0001_schema.sql` | Tables, indexes, triggers, the new-user hook |
| `0002_rls.sql` | Row Level Security on every table |
| `0003_retention.sql` | Data minimisation, account deletion, data export |

## Conventions

- UUID primary keys generated by the database; content tables keep their human-readable ids (`commercial-vente`, `res-gcf-excel`) because those ids are the join between the TypeScript modules and the database.
- `created_at` / `updated_at` on every mutable table, maintained by a trigger.
- Anything filtered, sorted or joined on gets a real column and an index. Nested structures that are only ever read as a whole are `jsonb`.
- Hard deletion where the UI promises irreversibility; soft deletion only where a user might want something back.

## Table groups

### Reference content — world-readable, admin-writable

`sectors`, `skills`, `career_paths`, `roadmap_stages`, `roadmap_items`,
`learning_resources`, `roadmap_resource_links`, `practical_projects`,
`interview_questions`

Seeded from `src/content/`. The application reads content from those modules at
runtime ([ADR-003](DECISIONS.md)); these tables exist so administrators can edit
it and so future tooling can query it.

Two constraints worth noting:

```sql
-- A link cannot claim verification without the date it was verified.
constraint learning_resources_verified_needs_date
  check (verification <> 'verified' or last_reviewed is not null)
```

```sql
-- Unpublished pathways are invisible to non-admins, so a draft can exist safely.
create policy "career_paths_public_read" on public.career_paths
  for select using (published or public.is_admin());
```

### Admin overlay and audit

`content_overrides` — admin edits keyed by `(kind, ref_id)`, merged over the
seed at read time so the original is always recoverable.

`content_reviews` — who checked what, when, and with what outcome. This is the
audit trail behind the link-verification promise.

### User data — owner-only

`profiles`, `user_preferences`, `onboarding_responses`,
`profile_skill_assessments`, `user_roadmaps`, `user_progress`, `user_notes`,
`saved_resources`, `weekly_plans`, `weekly_tasks`, `user_projects`,
`portfolio_entries`, `skill_gaps`, `value_propositions`,
`interview_practice_answers`, `star_examples`, `confidence_work`,
`cv_profiles`, `checklist_states`, `employer_research`

One policy shape, applied to all of them:

```sql
create policy "<table>_owner_all" on public.<table> for all
  using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

**Administrators are deliberately excluded.** The admin area shows aggregates
only; nobody should be able to read a young person's CV, interview answers or
confidence notes.

`user_progress` is unique on `(user_id, item_id)`, which is what makes
replaying a queued offline completion idempotent.

### Job analysis

`job_descriptions` → `job_requirements` (normalised, queryable) and
`job_analyses` (jsonb extraction + comparison).

A guest may analyse an advert without an account. Those rows have a null
`user_id`, are unreadable by anyone, store an empty `raw_text`, and are purged
by `purge_anonymous_job_data()`.

### Feedback and metrics

`feedback` — insert-allowed for everyone, readable only by admins. Email is
stored only when the sender asked for a reply.

`metric_counters` — `(event, count)`. No user id, no session id, no timestamp
beyond `updated_at`. RLS allows admin reads only; writes go exclusively through
`increment_metric()`, a `SECURITY DEFINER` function, so a client can count but
can neither read nor forge the totals.

## RLS model

RLS is enabled on **every** table. A table without a matching policy denies all
access, which is the correct default.

`public.is_admin()` is `SECURITY DEFINER` so an admin check inside a policy on
`profiles` does not recurse into that same policy.

### Admin provisioning

Postgres RLS cannot express "update every row except this one column", so
`profiles.is_admin` is not protected by a column-level rule. The application
never exposes it and provides no path to set it. Administrators are provisioned
deliberately:

```sql
update public.profiles set is_admin = true where email = 'admin@example.org';
```

`ADMIN_EMAILS` is a bootstrap allowlist for the first administrator and for the
local driver, which has no database to read the flag from. The database flag is
authoritative when both exist.

## Retention and user rights

| Function | Purpose |
| --- | --- |
| `purge_anonymous_job_data(interval)` | Deletes guest job adverts after 7 days |
| `delete_account(uuid)` | Hard-deletes the caller's account; cascades everywhere. Anonymises rather than deletes rows that fed aggregate counters, so counts stay correct without retaining anything identifying |
| `export_my_data()` | Returns everything held about the caller as one JSON document |

`delete_account` refuses any target other than `auth.uid()`.

Schedule the purge with pg_cron, a Supabase scheduled function, or external
cron. It is a plain SQL function so it works on any plan.

## Local driver

The development driver stores the same logical tables as JSON in
`.data/db.json`. It has no RLS — the process has full access to the file — and
no concurrency control beyond an in-process lock and an atomic
write-then-rename. `productionConfigIssues()` blocks it from passing silently
into production.

## Changing the schema

1. Add a new numbered file in `supabase/migrations/`. Never edit an applied one.
2. Update the matching types in `src/lib/types.ts`.
3. Update the mappers in `src/lib/db/repository.ts`.
4. Add or update RLS policies in the same migration — a new table with no policy is inaccessible, which is safe but confusing.
5. Run `npm run db:migrate`, then `npm test`.
